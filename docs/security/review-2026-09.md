# Security review, September 2026

**Scope:** an adversarial review of the merged application, before first production use.
Issue [#41](https://github.com/bherila/e-sign/issues/41).

**Reviewed at:** `main` @ `46fbcca`, plus the fixes in this branch.
**Not reviewed:** the Firma compatibility facade (`app/Http/Controllers/Compat`,
`app/Domain/Integration/Firma`, and the facade's additions to `routes/api.php`), which is in
flight on another branch and is not merged. Issue
[#33](https://github.com/bherila/e-sign/issues/33) owns its review.

**Method.** Five parallel passes over guest access, the signing state machine, service
credentials and the native API, outbound destinations and webhooks plus mail, and evidence,
retention, and uploads — each reading the code against the invariants in
[`docs/HANDOFF.md`](../HANDOFF.md) sections 8–12 and the module documentation, and each asked
to state explicitly what it checked and found sound as well as what it found wrong. Every
finding below was then reproduced before it was fixed. Nothing here is a static-analysis
result nobody executed.

**Baseline and result.** 1,696 tests before, 1,739 after. 65 findings: **39 fixed or
corrected**, **20 accepted residuals** with the reasoning recorded (two of which are also
tracked as open work), **6 open with a named owner**, and **2 raised and found sound on closer
reading**. Every fix carries a test that fails
without it, and each of those tests names the finding it pins.

## Findings

Severity is about this product's own threat model: **high** means it breaks an invariant
`docs/HANDOFF.md` states, **medium** means it is exploitable by somebody who is already
supposed to be there or by an unauthenticated caller at limited cost, **low** means it is a
real weakness with a narrow path or a bounded consequence, **info** means it is latent — sound
today, and a hazard for the next person.

## Guest access

### G-1 — the per-address OTP ceiling confirms an address (medium, fixed)

`app/Http/Controllers/Signing/LegacyRecipientResolverController::request()`.

The compatibility resolver's design goal is stated in
[`docs/signing/guest-access.md`](../signing/guest-access.md): *"The response after an address is
submitted is byte-identical whether the address matched or not."* It was not.

`OtpChallenges::issue()` is only reached on the branch that runs when the address **matched**,
and it hits a per-destination-address ceiling (`signing.otp.per_address_per_hour`, 5). Exceeding
it throws `GuestRateLimited`, which the controller turned into a distinguishable 429 page with
`Retry-After`. A non-matching address always produced the neutral 200.

**Reproduction.** With the shipped defaults, post a candidate address six times to
`POST /signing/{recipientPublicId}`. A 429 on the sixth means the guess is the address on the
envelope; six 200s mean it is not. The per-client ceiling for this endpoint is 20/hour, so one
address is confirmed or eliminated per ~6 requests, three candidates per hour per source
address, trivially parallelised. The measured behaviour, with the ceiling lowered to 2 for
speed, was `RIGHT status: 429  WRONG status: 200`.

**Fix.** The two limiters are now handled differently, because they mean different things. The
per-client `legacy_resolve_per_ip` ceiling is counted on every call regardless of the address,
so its 429 is a fact about the caller and is reported. A refusal from inside the matched
branch is swallowed and the neutral page returned. The ceiling is still enforced — no challenge
row, no mail — and only the disclosure is withheld.

**Residual.** A matched address does more work (a challenge row, an outbox row, a rendered
mail), so the two paths differ in response time. That is a timing side channel on an endpoint
that is already rate-limited per client, against a value an attacker must already have guessed
in full. Removing it would mean enqueueing a discarded message for every wrong guess, which
trades a measurable oracle for a mail-flooding primitive.

### G-2 — a signature payload is decoded before its size is checked (low, fixed)

`app/Domain/Signing/Capture/SignatureImage::reencode()` measured `strlen($binary)` — the
*decoded* bytes — against the 200 KB ceiling. Reaching that line costs a `preg_match` over the
whole submission, a capture-group copy, a whitespace strip, and a `base64_decode`. With the
shipped `public/.user.ini` (`post_max_size = 64M`) a single field could spend all of it, so a
value three hundred times its own ceiling was several copies of 64 MB before it was refused.
Bounded by `memory_limit = 512M`, so this is amplification rather than a crash, on an
authenticated guest session.

**Fix.** The encoded length is measured first, against `maxBytes * 2` — comfortably above the
~1.34× base64 expansion of a submission at the ceiling, and far below anything that could
matter. An oversized submission now costs one `strlen`.

### G-3 — the resolver is an unthrottled existence oracle (low, accepted)

`GET /signing/{recipientPublicId}` and `GET /sign/{envelope}/{token}` carry no rate limit: a
recipient that exists renders a form (200), one that does not is a router 404. So an
unauthenticated caller can probe recipient identifiers at whatever rate the host allows, and
each probe costs one indexed query.

**Accepted, with the reasoning.** A recipient `public_id` is a ULID: 48 bits of timestamp and
80 bits of randomness. Enumeration at ten thousand requests per second for a year covers about
2³⁸ of a 2⁸⁰ space. What remains is an unauthenticated database-query surface, which is the
same shape as every other public GET in the application and belongs to whatever fronts it. The
POST steps that do anything are limited (`legacy_resolve_per_ip`, `session_start_per_ip`,
`otp_verify_per_ip`).

### G-4 — the threat model overstates ULID entropy (info, corrected)

`docs/signing/guest-access.md` said a guessed recipient identifier is *"128 bits away"*. A ULID
is 48 bits of millisecond timestamp and 80 bits of randomness, and the timestamp of an
envelope's creation is often approximately known. 80 bits is still far out of reach; the
sentence was wrong by 48 bits and is corrected.

### Checked and sound

The invitation and session credentials are 256 bits from `random_bytes` stored as SHA-256
verifiers, looked up by digest so no timing signal about the plaintext exists; the invitation is
consumed by a compare-and-swap on `consumed_at IS NULL`; issuing revokes every live invitation
for the recipient. `RequireSigningSession` compares the session's envelope against the URL's, is
resolved in middleware rather than by implicit binding so a controller signature change cannot
disable it, and deliberately does not check eligibility so a signer who has already signed gets
an explanation rather than a 403. The `esign_signing` cookie is host-only, `Path=/sign`,
`HttpOnly`, `SameSite=Lax`, `Secure` in production, and a session cookie. All four GETs are
side-effect free and `HarmlessGetTest` fetches every one twice and diffs the envelope, every
recipient, every field value, every attestation, every invitation, every OTP challenge, and the
outbox. Every POST in `routes/signing.php` is CSRF-protected and a test asserts the middleware
list. `ReturnUrlPolicy` is an exact-host allowlist, empty by default, with no suffix matching,
silently ignoring anything else so the parameter is not an allowlist oracle; the accepted value
is stored on the session and re-read from there. Other parties' email addresses are replaced
with an RFC 2606 `.invalid` placeholder in the page payload. Signature capture refuses a remote
URL, SVG by name, a declared/sniffed type mismatch, and anything GD cannot decode, and
re-encodes through a pixel buffer with dimension and byte ceilings applied before decode. A
`Log::spy()` test asserts a full landing-plus-start-plus-refusal sequence logs nothing at all.

## Signing state machine

### S-1 — a required checkbox stored as `false` counts as complete (high, fixed)

`app/Domain/Signing/Envelopes/EnvelopeStateMachine::assertRequiredFieldsComplete()` tested
`isset($stored[$field->id])`, and `storedFieldIds()` built that map from row presence alone —
`array_fill_keys($ids, true)`. The value was never inspected.

`FieldMateriality` describes a tick box beside a term as *the term being accepted*. The shipped
fixture's `buyer_ack` is a required checkbox. `FieldValueValidator::boolean()` accepts `false`
as a valid checkbox value, so writing it creates a row.

**Reproduction.** A legitimate recipient with a live session posts
`{"values":{"buyer_ack": false}}` to `POST /sign/{envelope}/session/values`, fills the signature
box normally, and accepts. The acceptance succeeds and the attestation binds a material digest
in which the acknowledgement is `false`. The only code that knew `false` is not an answer was
`hasValue()` in `resources/js/signing/fieldEntryReducer.ts` — the browser.

**Fix.** `storedFieldIds()` now returns only fields whose stored value counts as supplied, by
the client's own rule moved to where it is authoritative: `null` is nothing, `false` is a
refusal rather than an answer, and a string that trims to empty is a blank box. The rule lives
in the domain because the state machine is also reachable from a job and a console command.

### S-2 — a required text field of whitespace counts as complete (low, fixed)

The same defect for text. `FieldValueValidator::text()` rejects `''` and accepts `'   '`. In
practice Laravel's global `TrimStrings` and `ConvertEmptyStringsToNull` catch it on an HTTP
request — but that means the invariant was upheld by an HTTP middleware, and the state machine
is not an HTTP concern. Fixed by the same change.

### S-3 — an acceptance against a consent version nobody was shown (medium, fixed)

`accept()`'s consent check compares `$request->consentPolicyVersion` against
`$locked->consent_policy_version`. Both sides are the envelope's snapshot, so the check catches
a lying client and nothing else. The text actually rendered never enters it.

`ConsentPolicy::html()` always reads `resources/views/signing/consent.md` from disk.
`ConsentText::matchesRecordedVersion()` exists and was surfaced to the page as a warning banner —
and `canSubmit` in `ConsentPanel.tsx` did not include it. So on a deployment that bumped
`ESIGN_CONSENT_POLICY_VERSION` while envelopes created under the old version were in flight, a
signer was shown the new wording, warned, and allowed to sign, and the attestation recorded the
old version. `ConsentText`'s own docblock names this outcome as the thing it exists to prevent:
*"an attestation that says 'consent-2026-01' while the signer was shown 2027's wording is a
record of something that did not happen."*

**Fix.** Both ends. `AcceptAgreementRequest` refuses the acceptance when the on-disk version is
not the envelope's, and the client disables the button. Not attacker-triggered — it is a
deployment-state defect that manufactures false evidence, which is worse.

### S-4 — signing after expiry, before the sweep (medium, fixed)

`accept()` called `assertLegal('accept', $locked)`, which checks the state column. `expires_at`
is applied by `ExpireCommand`, scheduled hourly. So for up to an hour after an envelope's
expiry — and indefinitely if the scheduler has stopped — an envelope was still `in_progress`
and still took signatures. `routes/console.php` concedes the window in a comment; the check is
one `if` away and is now in `accept()`, inside the same lock as everything else. The sweep
still owns the transition and its event.

### S-5 — `updateDraft()` reads state and writes recipients without a lock (medium, accepted)

`app/Domain/Integration/Native/EnvelopeService::updateDraft()` tests
`$envelope->state !== EnvelopeState::Draft` outside any transaction, and `correctRecipients()`
then writes `name`, `email`, and `identity_snapshot` with a plain `save()` — no version
compare-and-swap, unlike every other writer in the module, which goes through
`commitRecipient()`.

A `PATCH` racing a `POST …/send` can therefore rewrite a recipient's address after the
invitation has been scheduled: the invitation goes to one address and the agreement records the
other, and `identity_snapshot` — which exists to record who this party was — is rewritten after
the fact.

**Accepted for now, and stated rather than hidden.** It needs a workspace credential acting on
its own envelope, the damage is evidence quality rather than authorization, and `save()` writes
only dirty columns so `state` and `version` are not clobbered. The fix is to move the draft
check and the recipient writes inside `withLockedEnvelope()` with a version predicate, which is
a change to the module the Firma facade is currently being built on and belongs in that change
rather than beside it. Tracked for #33.

### S-6 — a concurrent double-accept is reported as a stale review (low, accepted)

Two acceptances in flight for one session: the loser blocks on `lockEnvelope()`, resumes, and —
if its snapshot was established before the winner committed — sees version + 1 and gets a 409
"the agreement changed, read it again", which is false and alarming. Integrity holds: the
`unique(recipient_id, session_ref)` key and the version CAS mean one attestation either way.

**Not reproduced.** Under MySQL's REPEATABLE READ a locking read is a current read, and the lock
is the transaction's first statement, so the loser's replay lookup should see the winner's
attestation and return a replay as intended. SQLite serialises write transactions entirely.
Recorded because the reasoning is not airtight across engines and the failure mode is a
misleading page rather than a wrong record.

### S-7, S-8 — accepted residuals

`FinalizationInput` records each attestation's `material_values_sha256` and separately
recomputes `MaterialValues::forEnvelope()`, and never compares them — while the *document*
bytes are re-verified with `hash_equals` and refuse publication on mismatch. The freeze makes
material change after the first acceptance impossible, so this is a missing last line of
defence rather than a hole. Worth adding when finalization is next touched.

Any non-empty value write bumps the envelope version, and `accept()` demands exact equality, so
in parallel mode a party can loop value submissions and invalidate every co-signer's rendered
version. Fail-closed, self-limited to parties already on the envelope, and the alternative —
accepting a stale version — is the invariant this product exists to hold.

### Checked and sound

Cross-recipient field writes are refused at four independent layers: the schema ownership
comparison in `assertRecipientMaySubmit`, the derivation of the envelope *from* the recipient so
a mismatch is unconstructible, a unique `(envelope_id, schema_recipient_id)` index with a binary
collation, and the absence of any recipient parameter in any signing URL. Stale-review replay is
double-guarded inside one transaction and one lock: the version is compared after
`lockForUpdate()`, and the material digest is recomputed fresh through the query builder inside
the same transaction before it is compared. Sequential ordering, terminal-state re-entry, and
the concurrent-accept / finalize / cancel / expire races are covered by `EnvelopeRaceTest`,
`EnvelopeSigningOrderTest`, and `EnvelopeTransitionMatrixTest`, and `commitEnvelope` /
`commitRecipient` are single `UPDATE … WHERE version = ?` statements that throw when zero rows
change. Attestations refuse updates and deletes. Read-only required fields are demanded at
acceptance and guaranteed present by the send gate. `signing_date` is the only exemption, and it
is service-supplied by definition.

## Service credentials and the native API

### A-1 — nothing limits `/api/v1` (medium, fixed)

`bootstrap/app.php` never calls `throttleApi()`, so the framework's `api` group resolves to
`SubstituteBindings` alone, and no route file adds a `throttle`. The only `throttle` in the
whole application was `routes/mail-webhooks.php`.

Each failed authentication costs an indexed query and a `Log::warning` write with no dedupe. It
is not a path to a secret — 43 characters from a 36-character alphabet is not guessable — but it
is unmetered log and database load from an unauthenticated caller, and it is what would have
made A-5 into a usable oracle.

**Fix.** A per-client-address failure budget in `AuthenticateServiceCredential`, counted on
failures only so a working integration's throughput never depends on it, configurable via
`ESIGN_API_AUTH_FAILURES_PER_MINUTE` (30) and switchable off where an edge proxy owns it. A new
`too_many_requests` error code carries it in the native envelope with `Retry-After`.

Deliberately *not* a blanket request ceiling on the API. The consumer's polling volume is not
this review's to guess, and a limit chosen without that number would be an outage waiting for a
busy afternoon.

### A-2 — a webhook secret in cleartext in `api_idempotency_keys` (medium-high, fixed)

`ApiIdempotency` records every 2xx response body verbatim, and two endpoints — creating and
rotating a webhook endpoint — return `secret` in that body. `api_idempotency_keys.response_body`
was an unencrypted `longText`.

This contradicted [`docs/api/native-v1.md`](../api/native-v1.md) in as many words: *"Only
ciphertext is stored and there is no route that returns it again."* The endpoint's own
`secret_current` and `secret_previous` are `encrypted` casts; this copy was not. A database dump
or a read-only database compromise yielded plaintext signing secrets for anything created or
rotated in the previous 24 hours.

**Fix.** `'response_body' => 'encrypted'`, which is parity with how the same secret is stored on
the endpoint itself, and no new mechanism. The replay a dropped connection depends on still
works, which is why the body is recorded at all.

**Residual, and it is the right one.** A caller holding the credential *and* the exact
idempotency key can still re-read the response within 24 hours. That caller holds
`webhooks:manage` and could simply rotate again for a fresh secret, so it is not an escalation.

**Two operational consequences, handled rather than documented away.** Making a column an
`encrypted` cast means a row written before the change, or written under a previous `APP_KEY`,
can no longer be read. Neither is a reason to answer a caller with a 500 for the next 24 hours.
`IdempotencyStore::existing()` now discards such a row exactly as it discards an expired one —
a record that cannot be read is not a record — and the caller gets a real attempt.

### A-3 — the idempotency fingerprint omits the query string (medium, fixed)

`IdempotencyStore::hashRequest()` hashed method, path, and body. Every Form Request on this
surface reads its input through `validated()`, and `FormRequest::validationData()` is
`$this->all()`, which merges the query — so query parameters drive behaviour on mutating routes
while being invisible to the fingerprint.

**Reproduction.** `POST …/rotate-secret?grace_hours=24` with `Idempotency-Key: k1`, then
`POST …/rotate-secret?grace_hours=0` with the same key and the same empty body. Same
fingerprint, so the second is answered with a replay of the first: a 200 carrying a secret, and
**no rotation**. `grace_hours: 0` is documented as the right value when rotating *because* a
secret leaked, so this is the exact call where a silent no-op costs most.

**Fix.** The query string is part of the fingerprint, canonicalised by sorting so parameter
order cannot defeat a legitimate replay — the same courtesy the body already had.

### A-4 — an unmatched non-GET escapes the error boundary (medium, fixed)

`Route::fallback()` registers for `GET` only. So `POST /api/v1/anything` is refused by the
*router*, before route middleware, and `ApiErrorBoundary` never runs. The answer was Laravel's
flat `{"message": "The POST method is not supported for route … Supported methods: GET, HEAD."}`
— the wrong contract shape, a route-existence oracle, and with `APP_DEBUG` on, `exception`,
`file`, `line`, and a full `trace` with absolute paths on an endpoint that needs no credential.

`ApiErrorMap::debugDetails()` is double-gated and would not have leaked; this path never reached
it. **The guarantee `ApiErrorBoundary` makes is conditional on a route matching**, which its
docblock did not say.

**Fix.** A `MethodNotAllowedHttpException` render in `bootstrap/app.php`, where a router-level
refusal can still be caught, emitting `method_not_allowed` in the native envelope with no verb
list.

### A-5 — a prefix-existence timing oracle (low, fixed)

`AuthenticateServiceCredential` looked the credential up with `->with('workspace')`. Eloquent
skips the eager load when no row is found, so a **known** prefix cost a second `SELECT` that an
unknown one did not, and only the known prefix reached a digest and a `hash_equals`. Status,
body, and headers were already byte-identical.

The prefix space is 36¹² ≈ 2⁶², so this confirms a suspected or partially leaked prefix rather
than enumerating one — and a prefix is documented as the public half of a credential. It still
contradicts the explicit claim in
[`docs/operations/service-credentials.md`](../operations/service-credentials.md) that *"a caller
that has not proved it holds a secret learns nothing about which prefixes exist."*

**Fix.** No eager load; the workspace is loaded after the secret matches. A miss pays for an
equivalent digest and `hash_equals` against a dummy salt, so the two paths cost the same work as
well as the same queries. Asserted on query count, which is the deterministic half of the
statement — a stopwatch assertion in CI is a flaky test.

### A-6, A-7, A-8 — accepted residuals

`ApiIdempotency` runs before `RequireScope`, so a credential whose scopes were narrowed
out-of-band can replay a 24-hour-old key and still receive the cached body. Same credential
only — the key is scoped to `credential_id` — and there is no API to change scopes, so it takes
a direct database edit. The ordering is deliberate and correct for its stated purpose; it is
worth knowing that it also precedes authorization.

`routes/api.php`'s `{artifact}` pattern is `[A-Za-z0-9._-]{1,128}`, which matches `..`. Not
exploitable: the bound locator returns `null` unconditionally and the interface forbids treating
the id as a path component. Whoever writes the real locator (E-3) inherits the pattern, and
should tighten it in the same change. Not fixed here because `routes/api.php` is owned by the
facade branch.

`Cursor` is `base64url("v1:" . $lastId)` and is described as opaque; it is trivially reversible
and leaks the caller's own last row id. It is only ever used as `where(id, '>', …)` on an
already workspace-constrained query, so it grants no cross-tenant read.

### Checked and sound

`hash_equals` is the only comparison of secret material anywhere in the credential code. The
digest is a fast salted SHA-256 by a documented decision that holds for server-minted
222-bit secrets, with a fresh 128-bit salt per row. Scope satisfaction is enum identity — no
prefix match, no substring, no wildcard — and `RequireScope` requires all listed scopes, fails
closed with 401 on a missing principal, and throws on an unknown scope name in a route
definition rather than silently denying. `X-HTTP-METHOD-OVERRIDE` cannot bypass a scope, because
routing uses the overridden method and therefore matches the route whose middleware applies.
Every tenant lookup applies the workspace predicate **before** the identifier, including
`document_id` and `template_version_id` taken from a request body, so a cross-tenant id is a 404
and never a 403. Idempotency keys are scoped to the credential by a unique index and by every
query. Error bodies carry a fixed sentence for an unexpected failure and never a trace, a file
path, or a class name. Exactly one `Log::` call exists in the whole surface and it records the
public prefix and a reason; an exception whose message quotes the presented secret is replaced,
with `previous` deliberately dropped so the secret cannot ride the chain.

## Outbound destinations, webhooks, and mail

### D-1 — two prefixes pass the destination policy (low, fixed)

`https://[::ffff:0:7f00:1]/` — RFC 2765 IPv4-translated `127.0.0.1` — passed the entire policy
and was pinned for connection. It is the sibling of the IPv4-*mapped* `::ffff:0:0/96` that PHP
already treats as reserved, and the one transition prefix the extra-reserved list omitted.

The immediate cause is subtle and worth recording: `isInExtraReservedRange()` stripped a leading
`::ffff:` unconditionally, which turned `::ffff:0:7f00:1` into `0:7f00:1`, which `inet_pton`
rejects, so the whole check returned `false`. The strip now applies only when what follows is a
dotted quad.

`224.0.0.0/4` multicast also passed. Not reachable over TCP, listed for completeness because the
class's stated rule is that each prefix is refused whole.

### D-2 — a non-ASCII host is validated as bytes and pinned as bytes (medium, fixed)

The policy validated `$parts['host']` with `FILTER_VALIDATE_DOMAIN | FILTER_FLAG_HOSTNAME`,
resolved it through `gethostbynamel`, and pinned `CURLOPT_RESOLVE` under that exact spelling.
`FILTER_FLAG_HOSTNAME`'s alnum test is locale-dependent, and on a Latin-1-ish locale
`a\xffb.test` is accepted. libcurl built with libidn2 — which the usual `php:*-fpm` Debian image
is — IDN-converts the hostname *before* looking it up in the resolve table. When the two spell
the name differently, the pin misses, the cache misses, and **curl performs its own unvalidated
DNS resolution**.

The attack needs no rebinding race: register a name whose raw-byte form resolves publicly and
whose normalised punycode form resolves to `127.0.0.1`.

**Environment-dependent, and reported as unverified.** On a `C`-locale glibc host every byte
above 0x7F is rejected by the hostname filter, and the macOS curl this was probed on showed no
IDN conversion. The runtime image is not in this repository, so the premise could not be
confirmed here.

**Fix.** A host must be printable ASCII, checked before the hostname filter. An operator with an
internationalised domain converts it to punycode once, in configuration, where a human can read
it. Percent-encoding — the same class of pin-miss, since curl percent-decodes the host — was
already blocked incidentally, because `%` fails the hostname filter.

### D-3 — webhook delivery fails open without `ext-curl` (medium, fixed)

Address pinning exists only as cURL handler options, and Guzzle applies its `curl` array only
when the cURL handler is selected. Without `ext-curl` it silently falls back to `StreamHandler`:
`allow_redirects => false` and `verify => true` still hold, but `CURLOPT_RESOLVE` and
`CURLOPT_PROTOCOLS_STR` vanish, and the DNS-rebinding window between `validate()` and the
connection reopens — with no error and no failing test.

`HttpTimestampAuthority` already failed closed on exactly this condition.
`WebhookTransport` now does the same, and `composer.json` requires `ext-curl` (with `ext-gd`,
`ext-openssl`, and `ext-zip`, which were equally load-bearing and equally undeclared) so a
deployment finds out at install time rather than at delivery time.

### D-4 — a plaintext OTP persists indefinitely (medium, fixed)

The transactional outbox renders from a persisted context — that is what makes delivery survive
a crash — so a live code has to sit in `outbound_mails.context` between enqueue and send. Three
places in the codebase disclosed this residual and all three bounded it: *"for the ten minutes
it is worth anything"*, *"until that row is pruned"*.

**There is no pruning.** `outbound_mails` is not `Prunable` and nothing schedules a sweep of it,
and `RecipientEraser` rewrites only `recipient_name` and `actor_name` in the context, with a
comment stating that nothing else in it is contact data. So every one-time code ever mailed was
readable in the database and in every backup, for the life of the installation.

**Fix — this is the one issue #41 asked to be fixed if it was simple.** The code is dropped from
the persisted context in `markSentToProvider()`. Dropped on the way out rather than on a timer,
because it is needed for exactly as long as a render might still happen: a retry before a
successful send still has it, and `resend()` mints a fresh row from a fresh context.

The proposal in the issue — store a hash and render from a short-lived cache — was considered
and rejected. On the cPanel profile the queue is cron-driven, so the cache entry can expire
before the worker runs, and the failure mode is an OTP mail that cannot be rendered at all. It
also does not remove the exposure on a database cache driver; it moves it to a table with a TTL.
Scrubbing on send gets the same reduction with no new failure mode.

**Residual.** A code is readable in the database while its message is queued — seconds under a
worker, up to a cron interval on shared hosting. That is the host-administrator case
`docs/HANDOFF.md` section 8 already places outside this evidence model.

### D-6 — forged block structure through a decline reason (low, fixed)

`MailCopy` escaped `\ [ ] ` * _ ~ |` and deliberately left `#`, `>`, `-`, `+`, and leading
digits alone, on the reasoning that they *"can change block formatting at worst"*. That
understated it. A decline reason is typed by an external signer, is `max:500` with newlines
intact, and is rendered inside a `> ` blockquote in a notice the **sender** receives from their
own agreement service:

```
Wrong signatory.

# Your agreement was suspended

Call +1 555 0100 to restore it.
```

Only the first line stays quoted. No link can be injected either way — that was already
blocked and tested — but a forged heading in a message from a trusted service is a phishing
frame without one.

**Fix.** Block-opening markers are escaped where CommonMark reads them as a block start, and
only there, so ordinary prose containing a hyphen is untouched. An ordered list is escaped on
its delimiter (`1\.`) rather than its digits, because CommonMark honours a backslash only before
ASCII punctuation and `\1.` would render the backslash. A test asserts both halves: the forged
heading is inert, and `We are not proceeding - the terms changed.` comes back unchanged.

### D-10, D-11 — the SES feedback path, raised by #35 (medium, fixed)

Two findings from implementing SES feedback rather than from this pass. Recorded here because
both are about whether a delivery state can be trusted.

**D-10 — SES feedback was unauthenticated in principle.** `SnsMessageVerifier` had one
implementation, `RejectingSnsMessageVerifier`, which refused every message. That failed closed
and was the right call at the time; the consequence was that SES delivery feedback never
landed at all, so no message could leave `sent_to_provider` and the honest-states design had a
provider it could not use. The hazard was in what a naive fix would have looked like: accept
the body, or verify the signature and stop there. A valid SNS signature proves only that *some*
AWS customer signed the message, so signature-only verification would have let any AWS account
mark this deployment's mail bounced.

**Fixed** by `AwsSnsMessageVerifier` over `aws/aws-php-sns-message-validator` (AWS's own
canonical string-to-sign, so the field-order-per-message-type problem is not re-solved locally),
plus four things the library does not do: a topic ARN allowlist that is also the on/off switch,
SignatureVersion 1 (SHA-1) refused unless explicitly enabled, a replay window on `Timestamp` in
both directions, and a certificate fetch that goes through the shared `DestinationPolicy` and is
cached — the library's default is `file_get_contents($certUrl)`, which on an unauthenticated
endpoint is both an SSRF primitive and a fetch amplifier. With no topic configured the rejecting
verifier is still what the container binds, so an unconfigured deployment is exactly as closed
as it was. Refusals are recorded as `outbound_mail_events` rows with their reason, collapsed to
one per reason per window so a public POST surface cannot be turned into unbounded row growth.

**D-11 — the identifiers could never match.** Feedback is matched to a row by Message-ID and
nothing else, which is the right rule. But SES reports `mail.messageId`, its own identifier,
while Laravel's `Illuminate\Mail\Transport\SesTransport` records the SES id only as the
`X-Message-ID`/`X-SES-Message-ID` headers and never calls `SentMessage::setMessageId()` — so
`outbound_mails.message_id` held the locally generated RFC 5322 header instead. On
`MAIL_MAILER=ses` every notification would have been filed as an orphan, indefinitely, with no
error anywhere: the endpoint would have answered 200, the rows would have accumulated, and
every message would have sat at `sent_to_provider` looking like a provider that never reported.

**Fixed** at the one place that writes the column: `OutboundMailSender` prefers the
`X-SES-Message-ID` header when the transport set one. Rows written before the fix stay
matchable through a fallback on the `Message-ID` in SES's `mail.headers`, which SES includes
when the notification is configured to carry original headers. The SMTP-to-SES path was already
correct — Symfony parses the id out of the `250 Ok` reply — which is why this was invisible
until the API transport was considered.

### D-5, D-7 — accepted residuals

The signing URL is persisted verbatim in `outbound_mails.context` and is not tombstoned by
erasure. Invitation links are one-shot and revoked on re-mint, which mostly defuses it; a
completion **download** URL's lifetime depends on a minter that is currently
`UnconfiguredDownloadUrlMinter`, so whoever binds a real one owns this question.

`WebhookEndpointManager` records the endpoint URL unredacted in the audit trail on create and
update. The policy refuses credentials in the authority but not a query-string token, which is
how many receivers authenticate. The audit table is append-only by design and is not a place to
start rewriting values, so this is a note for the operator rather than a code change.

### Checked and sound

Every destination check is on the **resolved address**, never on the spelling, so octal,
decimal, short-form, `localhost`, and `nip.io`-style names are all judged on what they resolve
to. A host resolving to both a public and a private address is refused outright rather than
left to connection ordering. The destination is re-validated **per attempt**, not once at
endpoint creation, and the connection is pinned with `CURLOPT_RESOLVE` to every address that was
checked. Redirects are off at both the Guzzle and the cURL layer, and `CURLOPT_PROTOCOLS_STR`
is narrow. Plaintext HTTP cannot be enabled by anything a tenant controls; the only opt-in is
scoped to the TSA's own copy of the policy. Every outbound HTTP call in `app/` goes through the
policy — webhooks, the timestamp authority, and both SNS calls (the subscription confirmation
and, since #35, the signing-certificate fetch), each of which is additionally host-pinned by
pattern before a name is resolved. Webhook secrets are `encrypted` casts, are in `$hidden`,
never enter an audit payload or a queue payload, and `webhook_deliveries` stores no request
headers and no request body at all. `TextRedactor` strips control characters including `\x1B`
before truncating, so a hostile response body cannot inject ANSI into a console table. Signature
timestamps are fresh per attempt while the event id is stable across every retry and replay, and
`docs/delivery/webhooks.md` states plainly that replay protection inside the window is the
receiver's. In mail, every context field is Markdown-escaped and Blade-escaped, the action URL
is shape-validated and used only in a Blade attribute, and header injection is blocked by
Symfony's RFC 2047 encoded-word rule.

## Evidence, finalization, and sealing

### E-1, E-2, B-6 — what an erasure does not reach (medium, accepted and documented)

`RecipientEraser` tombstones `envelope_recipients.{name,email,identity_snapshot}` and the
addressing and name fields on the transactional messages (widened to every mail kind, and to
the address inside `context` and `outbound_mail_events.payload`, by
[#89](https://github.com/bherila/e-sign/issues/89)). Its audit event asserts a `retained`
list. That list is incomplete, in three places:

1. **`finalization_runs.input_snapshot`** contains each attestation's recipient `name` and
   `email` in a plain JSON column.
2. **`outbox_events.payload` and `canonical_body`** contain them in every `signing_request.*`
   event, and `OutboxEvent` refuses deletion.
3. **The published completion report** renders `Name <email>` on the page that is also appended
   to the executed PDF.

**Accepted, and this is a decision rather than an omission.** All three are inside something
digested: `input_snapshot` is covered by `finalization_runs.input_sha256`, `canonical_body` is
the exact bytes a webhook signature was computed over, and the completion report is inside a
sealed artifact whose SHA-256 is published evidence. Rewriting any of them would break a digest
the product asks relying parties to check — trading a verifiable record for a partial erasure.
`RecipientErasureTest` already pins that the executed PDF still carries the signer's name,
and the same reasoning covers the address.

What changes is the documentation: `docs/operations/retention.md`'s "what is not erased" section
now names these three, so the runbook's retained list is complete and an operator answering a
deletion request knows what to say.

### E-3 — published evidence has no HTTP route (medium, out of scope)

`IntegrationServiceProvider` binds `ArtifactLocator` to `NoArtifactsYetLocator`, and
`EvidenceServiceProvider` never rebinds it — so `GET /api/v1/envelopes/{id}/artifacts` and
`.../download` return `501 unsupported` for every completed envelope, and
`ArtifactDownloader::stream()` and `EvidenceExporter::bundle()` have no caller outside tests.

Not a vulnerability; a wiring step that finalization's own docblock says would be done in a
service provider. It belongs to issue [#30](https://github.com/bherila/e-sign/issues/30) and is
recorded in [`release-gates.md`](release-gates.md) rather than fixed here, because binding a
real locator changes the artifact API surface the facade branch is also touching.

### E-4 — `zend.exception_ignore_args` is assumed, not set (low, fixed)

`AuthenticateServiceCredential` and `docs/operations/service-credentials.md` both advise keeping
*"PHP's default `zend.exception_ignore_args=On`"*. The ini **default is Off**; `On` comes from
`php.ini-production`, which the official images ship but do not activate. Neither
`.docker/php/php.ini` nor `public/.user.ini` set it, and `.user.ini` does not apply to the CLI
queue worker — the one role that holds the seal key.

The unmitigated frame is `TcLibPdfSealer`, which passes the decrypted private key PEM inside an
array to a vendor method carrying no `#[\SensitiveParameter]`. Not a confirmed leak: the only
sinks are `__toString()` and `getTraceAsString()`, which render an array argument as `Array`,
there is no Sentry/Flare/Ignition in the dependency set, and `app/Domain/Evidence/` contains no
logging call at all. Both ini files now set it.

### E-5 — seal-preflight messages reach an API caller (low, fixed)

`SealMaterialAssurancePolicyCheck` returned `$exception->getMessage()` from a catch-all
`\Throwable` branch, which reaches `SendPreconditionsFailed::$problems` and then the 422 body of
any `envelopes:write` caller. The typed `SealMaterial*` messages are deliberately path-free and
are safe to forward; the catch-all is not — an unanticipated `ErrorException` could name the
seal key's path, which on the cPanel profile sits next to `.env`. The branch now returns a
generic sentence and points the operator at `esign:seal:status`, which is where a key path
belongs.

### E-6, E-7, E-8 — accepted residuals

`evidence.json`'s `validation_report.revisions` is `substr_count($pdf, '%%EOF')`, which an
uploader can inflate with a literal `%%EOF` inside a content stream. It is not a gate —
`isValid()` and `reachedLevel()` do not read it — but it is a published evidence field whose
value an uploader can make wrong. Worth replacing with a structural count when the validator is
next touched.

`/ByteRange` and `/SubFilter` are located by regex over the whole file rather than by an xref
walk, so a decoy can be placed after the real signature dictionary. This **fails closed**: the
CMS is then verified over the decoy range and fails, `cryptographicallySound` is false, and the
sealer refuses to return the artifact. Recorded so the reasoning is not re-derived.

The export omits `original-upload.pdf` when the reviewed revision *is* the original, and the
manifest does not say so — a reader cannot distinguish "same file" from "missing file". A
manifest note would close it.

### Checked and sound

`markCompleted()` has exactly one caller, inside `publish()`'s transaction, and the read-back
before it is a real streaming read through the storage adapter with a `hash_equals` comparison —
never an ETag, and a test greps the whole of `app/` for the word. A failed read-back throws and
nothing is published. Publication is three guards under a fresh row lock plus a database unique
key. The reviewed revision is re-read from storage and compared against the frozen
`document_sha256`. No queued class or Mailable holds seal material as a property;
`FinalizeEnvelope` carries a single string. B-T fails closed on every transport outcome and is
guarded twice — the sealer re-reads its own output, and the finalizer validates independently —
so a B-B artifact can never be published against a B-T request, and the TSA URL goes through the
same outbound policy with the same pinning and no redirects. Every digest covers the object it
names, none is self-referential, and the executed PDF's hash is computed outside the PDF. Every
zip entry name in the export is a hardcoded literal, so no document title, recipient name, or
uploaded filename reaches one; there is no import side and therefore no zip-slip. The export
re-verifies every member's digest and is refused rather than shipped on a mismatch. Artifact
downloads pin the content type from the artifact's kind, set `nosniff` and `private, no-store`,
and build the filename from a slug plus a digest prefix, so header injection is impossible.
Nothing presigns on any driver.

## Retention and legal hold

### B-1 — the pruner can delete every published artifact, hold included (high latent, fixed)

`PruneStagingArtifactsCommand` enumerated objects under the artifact root and built its
"referenced" set as `artifacts WHERE disk = config('esign.documents.disk')`. But `artifacts.disk`
is **frozen at publication**. Rename `ESIGN_DOCUMENTS_DISK` — the same-bytes-new-name migration
[`docs/BLOB_STORAGE.md`](../BLOB_STORAGE.md) §1 explicitly contemplates — and every historical
row keeps the old name while the command enumerates the new one. The referenced set comes back
empty, every published object is "unreferenced", and after the age filter `--apply` deletes all
of it: executed PDFs, completion reports, evidence documents, **including envelopes under legal
hold**.

This is the one evidence-deleting path in the application with no legal-hold consultation at
all — grep finds neither `LegalHold` nor `legal_hold_at` in the file. Its only protection is set
membership, and set membership is exactly what breaks. `docs/BLOB_STORAGE.md` §3 prescribes the
two controls that would have caught it, and neither was implemented.

**Fix, three parts.** The referenced set is read across every artifact row regardless of the
disk name a row records — a path is a content-addressed key under one root, and the failure mode
of a too-wide set is that an orphan survives another day. The implausible-scale abort
`docs/BLOB_STORAGE.md` asks for refuses when more than half the enumerated objects look
unreferenced. And `--older-than` has a floor (B-2).

Two tests: a renamed disk leaves every published artifact in place, and an empty referenced set
is refused rather than acted on.

### B-2 — `--older-than=0` and an unverified publication (medium, fixed)

`ageInSeconds()` matched `^(\d+)([dhms]?)$` with no floor, so `--older-than=0` put the cutoff at
`time()` and an object written in the same second was old enough to delete. Rule 3 of the
command's own contract — *"A minimum age"* — was documentation, not code.

The consequence compounds, because `EnvelopeFinalizer::publish()` checks state, generation, and
artifact-row absence but **not that the uploaded objects still exist**. An object deleted
between step 2 and step 3 produces a `completed` envelope, immutable artifact rows, a
`signing_request.completed` webhook, and no bytes — discovered days later by
`esign:artifacts:verify`, when the row can no longer be changed.

**Fixed:** a one-hour floor on `--older-than`, far longer than the gap between an upload and its
publication (a B-T seal's TSA round trip is seconds). **Not fixed:** the missing existence
re-check in `publish()`, which is a change to the finalization transaction and is recorded here
for whoever next touches it.

### B-3 — the sweep hard-deletes soft-deleted documents (medium latent, fixed)

`RetentionSweeper::unreferencedDocumentCandidates()` filtered on `created_at` and
reference-existence only, with no `whereNull('deleted_at')` — unlike its sibling
`abandonedCandidates()`, which has one. `applyUnreferencedDocuments()` then hard-deletes rows
and blobs.

That contradicts `docs/operations/retention.md` (*"a soft-deleted row still counts as a
reference … breaking it would make a reversible soft delete permanent"*), `docs/BLOB_STORAGE.md`
(*"reap blobs only once the row is hard-deleted"*), and `BlobPurger`'s own docblock. Not
reachable today, because nothing in the application calls `->delete()` on a `Document` — the
first "delete document" button would have turned an undo into destruction on the next sweep.
One clause, added.

**Follow-up ([#89](https://github.com/bherila/e-sign/issues/89)).** The clause was in the plan
only, and rule 5 of the sweeper's own contract is that *"every deletion re-checks its own
predicates at the moment it runs"* — a plan is printed to a human first, and the soft delete
the exclusion exists for can arrive while they read it. `applyUnreferencedDocuments()` now
re-reads `deleted_at` per document and reports the skip. The two tests named above cover the
plan and the apply side separately, and `LegalHoldTest::test_no_deletion_path_removes_a_held_envelope_or_a_soft_deleted_document`
walks every deletion path in the application in one pass with a held envelope and a
soft-deleted document present.

### B-7 — erasure has no envelope-state guard (medium, fixed)

`RecipientEraser` refused an empty reason, a missing envelope, an active hold, and a repeat
run — and never checked the envelope's state, although the operation's entire justification is
that contact data has no evidential role *once the agreement is executed*.

Erasing a live envelope's recipient rewrites the address invitations and one-time codes go to,
so the signer becomes unreachable and the agreement hangs until expiry. Worse: if the remaining
parties finish, `FinalizationInput::capture()` reads the recipient's email at render time, so
the sealed executed PDF and the completion report name that party as
`Erased recipient <erased-…@erased.invalid>` — permanently, in the instrument, under the service
seal.

Erasure now requires a terminal state (`completed`, `cancelled`, `declined`, `expired`,
`finalization_failed`) and says so.

### B-8 — destructive retention commands run during a restore drill (medium, fixed)

`RestoreDrill::assertNotDrilling()` guards `MailOutbox`, `OutboundMailSender`,
`WebhookDispatcher`, and the webhook job — deliberately at both the enqueue and the send end —
and guarded none of `esign:retention:run`, `esign:retention:purge-blobs`, or
`esign:artifacts:prune-staging`. A drill instance holds a full copy of production, including
real `deleted_at` values, and `ConfirmableTrait` prompts only when `APP_ENV=production` while
the drill runbook mandates `APP_ENV=drill`. So `purge-blobs` would run unprompted against
whatever bucket the copied `.env` names. Deletion is at least as irreversible as a mailshot; the
two retention commands now refuse.

### B-4, B-9 — accepted residuals

`BlobPurger` selects on `deleted_at` alone, with no check that retention was what soft-deleted
the row and no check that `executed_documents_days` is configured. The safety property the whole
runbook rests on — executed agreements are never deleted automatically until an operator sets a
reviewed value — lives only in `RetentionSweeper`. Nothing else writes `envelopes.deleted_at`
today, and `$fillable` excludes it, so this is latent: the first other writer inherits "destroy
this agreement's bytes in 30 days" on a deployment that never configured a policy. Worth a
`retention_scheduled_at` column rather than an inference from `deleted_at`, which is a schema
change and not a review fix. Since [#89](https://github.com/bherila/e-sign/issues/89) the
inference is stated where somebody would act on it — in `BlobPurger`'s docblock and in
`docs/operations/retention.md` — so the residual is documented rather than only recorded here.

A legal hold restrains deletion and not mutation, so a workspace credential can still rewrite
the parties on a held draft. `LegalHold` is honest that a hold is *this application's* deletion
restriction, and this may be intentional — but a preservation notice usually also means "do not
alter", and the runbook does not say which is meant. A question for counsel more than for code.

### Checked and sound

Legal hold is applied on every other evidence-deleting path, and applied twice: excluded in the
plan and re-checked against a live model at apply time, with the exclusion counted and printed.
`BlobPurger` re-checks the hold on a `withTrashed()` model at the moment of purge, and skips a
restored envelope. **No cascade delete touches evidence** — every foreign key on an
evidence-bearing table is `restrictOnDelete`, and the only `cascadeOnDelete` in the whole schema
are on auth attempts, passkeys, identity bindings, and idempotency keys. Model-level refusals
throw rather than soft-fail on `Artifact`, `RecipientAttestation`, `DocumentRevision`,
`AuditEvent`, `OutboxEvent`, and a published `TemplateVersion`. No HTTP route and no queue job
deletes an envelope, a document, a workspace, or a user. Erasure cannot break the hash chain:
`AttestationDigest` binds the recipient's public ULID and never a name, an address, or an
identity snapshot, which was verified against the digest's inputs rather than assumed. Policy
parsing maps `null`, `''`, `'0'`, negatives, and booleans to "this pass does not exist".

## Uploads and preflight

### U-1, U-2 — the parser can be made to exhaust memory from a small file (medium, mitigated, open)

The decompression ceiling `max_decoded_stream_bytes` (32 MiB) is **per stream**, and the parser
retains the decoded payload of every stream for the whole of preflight. Sixteen Flate streams,
each ~32 KB compressed and inflating to just under the ceiling, is a ~500 KB upload and ~500 MB
retained — fatal at `memory_limit = 512M`. Separately, `max_objects` is checked *after* the full
parse, and nothing bounds the entry count an xref **stream** declares, so a few kilobytes can
materialise a million entries before any application ceiling is consulted.

Both run **synchronously inside the web request**. Both need an authenticated workspace member
with upload rights.

**Mitigated, not fixed.** The upload route now has a per-member ceiling
(`RateLimiter::for('document-uploads')`, 30/minute), which bounds how often one member can
trigger it. That is not the fix. The fix is an aggregate decoded-byte budget and an xref-entry
cap applied *before* decoding, which means either a change inside `tecnickcom/tc-lib-pdf-parser`
or a pre-parse structural scan in this repository — a real piece of work, and this review's job
is to say so rather than to attempt it in a hardening branch. Recorded in
[`release-gates.md`](release-gates.md).

### U-3, U-4 — the hazard scan fails open (medium, accepted, open)

`TcPdfPreflight::scanEntry()` returns silently at depth 32. The parser accepts nesting to 256,
so a document may legally carry a directly-nested chain 33–256 levels deep in which every `/JS`,
`/XFA`, `/EF`, `/Launch`, and signature marker goes unclassified — and the document is accepted
with no finding at all. `PageTreeReader` **throws** when its depth cap trips, which is the
correct shape; the hazard scanner has the opposite behaviour, and `config/esign.php` documents
the 32 as intentional without saying it is non-fatal.

Separately, an xref entry whose offset lacks a matching object header degrades to a `null`
object rather than an error, so a hazardous dictionary can be hidden by corrupting only that
one entry — while Acrobat and PDF.js reconstruct the table and do see it.

**Accepted for now, and not because they are harmless.** Weaponising U-3 needs a viewer that
also descends past 32 *direct* levels for the hidden structure, which was not demonstrated;
spec-shaped hazards sit behind indirect references, and each indirect object is rescanned at
depth 0. U-4's fix — treat "an xref entry resolved to null" as a rejection — risks refusing
legitimate documents containing genuine null objects, and choosing between those needs a corpus
this repository does not have. Both are the kind of change that should land with fixtures and a
deliberate false-positive budget, not in a review branch. Open.

### U-5 — a rejected original is served inline (low-medium, fixed)

`DocumentIntake` stores the original *before* the accept/reject decision, deliberately, so a
rejected upload can be examined. The 422 that refuses it returns the document and its revision
ids. The download routes accept any revision of the document with only `View` permission, and
the `view` route serves it `Content-Disposition: inline`.

So an uploader received the exact inline URL for bytes policy had just called unsafe —
JavaScript, XFA, a launch action, an embedded file — and could send it to a colleague or an
auditor in the same workspace, who would render attacker-controlled bytes inline from this
application's own origin. Native and Acrobat viewers execute PDF-level JavaScript.

**Fix.** The inline route 404s for a document in `preflight_failed`. The attachment route still
serves the bytes, which is what examining a rejected file actually wants: a file opened
deliberately, in a tool the investigator chose.

### U-6 — the intake temp file leaks on a fatal error (low, accepted)

`DocumentIntake::record()` unlinks its staged copy in a `finally`, which does not run on a PHP
fatal or an execution-time kill — both of which U-1 and U-2 induce inside that method. Each
attempt leaves up to 32 MiB in the system temp directory, and nothing sweeps `esign-intake-*`.
A disk-fill amplifier for U-1 rather than an issue of its own; it goes away when U-1 does.

### Checked and sound

Preflight genuinely runs and a parse failure is **fatal**, not a warning: anything thrown becomes
a `reject` with `unparseable`, `ignore_filter_errors` is false, `isAccepted()` means "no reject
finding at all", and a review revision is created only for an accepted document. Encrypted,
already-signed (four independent signals), and XFA documents are refused, and the parser decodes
`#xx` name escapes, so the classic `/XF#41` key-obfuscation bypass does not work. **There is no
TOCTOU between validation and storage**: the bytes are read once, the same in-memory buffer is
what preflight inspects and what is written, and the stored object is read back and re-hashed
against a digest computed streaming off the original upload. Declared MIME is never trusted.
Size is enforced twice, in the Form Request and independently by the parser. Page-tree recursion
is bounded by a depth cap that throws and a visited set spanning the whole walk that throws on
any revisit, so a cyclic `/Kids` is refused; the declared `/Count` is ignored. Storage keys are
built entirely from application-generated ULIDs and the content digest with a strict character
class, never from a filename; the filename is a display title only, stripped of every `\p{C}`.
Download responses pin the content type, set `nosniff`, and build the disposition through
`HeaderUtils::makeDisposition()` — pinned by a test that uploads the title
`../../etc/passwd"; rm -rf /\r\nX-Injected: 1`.

## Cross-cutting

### X-1 — the global CSP is not the configured one (high, fixed)

`config/csp.php` declared `'policy' => App\Csp\CloudflareCspPolicy::class`. That is
`spatie/laravel-csp` **v2**'s API. This repository pins and installs **v3**, whose
`AddCspHeaders` reads `presets`, `directives`, `report_uri`, and `report_to`, and never looks at
`policy`. The configured policy was inert.

`CloudflareCspPolicy extends Spatie\Csp\Policies\Policy` — a class v3 does not ship. It could
not be autoloaded at all; it survived only because a class-string in a configuration array is
not autoloaded until something instantiates it. Confirmed:
`Error: Class "Spatie\Csp\Policies\Policy" not found`.

So the policy every non-signing page actually carried was the package's own `Basic` preset. The
divergence that matters: **no `frame-ancestors`** (`Basic` sets `frame-src`, a different
directive), plus a nonce in `style-src` that nothing in `resources/` emits — which suppresses
the `'unsafe-inline'` beside it and breaks the inline `style` attributes React writes for the
field overlays.

Measured on `/login` before the fix:

```
Content-Security-Policy: base-uri 'self';connect-src 'self';default-src 'self';font-src 'self';
form-action 'self';frame-src 'self';img-src 'self';media-src 'self';object-src 'none';
script-src 'self' 'nonce-…';style-src 'self' 'nonce-…'
X-Frame-Options: NULL
```

**Fix.** `config/csp.php` is rewritten against the v3 API with an explicit directive list
including `frame-ancestors 'none'`, nonces off, and no third-party origin at all — the analytics
host the old policy named is not loaded anywhere in `resources/` and AGENTS.md forbids it on the
signing surface. `app/Csp/` is deleted. The new test reads the **emitted header** rather than the
configured intent, which is the whole lesson: a policy object nothing loads looks exactly like a
policy that works.

### X-2 — security headers on the signing surface only (high, fixed)

`bootstrap/app.php`'s `withMiddleware()` registered two aliases and nothing else.
`SigningSecurityHeaders` is attached in `routes/signing.php` and nowhere else. So `/`, `/login`,
`/dashboard`, `routes/documents.php`, `routes/templates.php`, `routes/editor.php`,
`routes/health.php`, and `/up` carried **no** `Referrer-Policy`, `X-Frame-Options`,
`X-Content-Type-Options`, or `Permissions-Policy` — and, per X-1, no `frame-ancestors` either.

Every authenticated page in that list publishes templates, deletes aliases, or saves field
geometry, and all of it was framable from any origin.

Partly masked in the Docker profile, where `.docker/nginx/nginx.conf` adds three of them at the
server level. **The cPanel deploy path adds none** — `htaccess-append.txt` contains only the PHP
handler block — so on the shared-hosting target the application was the only thing that could
have set them.

**Fix.** `App\Http\Middleware\SecurityHeaders`, appended to the global stack. It writes a header
only when one is not already present, so `SigningSecurityHeaders` stays authoritative on the
guest surface and its narrower CSP and `no-store` survive intact.

### X-3 — no HSTS anywhere (medium, fixed)

A repository-wide grep for `strict-transport` returned nothing: not the middleware, not the
nginx config, not `htaccess-append.txt`. A signing invitation carries a 256-bit bearer credential
in its URL path, and a single `http://` navigation to one puts it on the wire. Cookies are
`Secure`, which protects the cookies and not the token.

Emitted now on requests that arrived over TLS, `max-age` configurable via `ESIGN_HSTS_MAX_AGE`
and zero to disable. **`includeSubDomains` is deliberately not offered**: a deployment at an apex
domain would otherwise commit every sibling subdomain — including the identity provider's — to
HTTPS on this application's say-so.

### X-4 — an attacker `Host` can reach an emailed link (medium, fixed)

There is no `TrustHosts` registration, so any `Host` header is accepted.
`InvitationIssuer::urlFor()` built the link with `absolute: true`, which in an HTTP request roots
the URL generator at `$request->getSchemeAndHttpHost()`.

Under the documented `QUEUE_CONNECTION=database` the mail-scheduling job runs in a worker, where
the generator is rooted at `APP_URL`, so the link is safe. Under `QUEUE_CONNECTION=sync` — a
one-line `.env` change, and what CI's own smoke tests use — the job runs inline in the request
that sent the envelope, and the invitation URL, including a live 43-character token, is built
from the attacker's `Host` and mailed to the recipient. `MailContext::assertUsableActionUrl()`
validates scheme, userinfo, fragment, and query count, and does not check the host.

**Fix at the mint, not at the edge.** `urlFor()` roots the URL at `config('app.url')` and throws
when that is empty. A `TrustHosts` registration would also work and would break a Docker
health check that reaches the container by IP; rooting the credential-bearing link at the
configured origin makes the safe case the only case.

### X-5 — no way to configure trusted proxies (medium, mechanism added)

`.env.example` and `config/bherila-auth.php` both instruct the operator to configure Laravel's
trusted proxies, and there was no mechanism: no `TrustProxies` subclass, no
`$middleware->trustProxies()`, no `config/trustedproxy.php`.

The default is the safe one — `$request->ip()` is the socket peer, so `X-Forwarded-For` cannot
move a rate-limiter key or an evidence record, and `ClientFingerprint`'s docblock calls that the
honest outcome. The problem is the other side. Behind any reverse proxy, every per-IP ceiling
collapses to a single bucket, and — more seriously — `HealthController::isFromAllowedSource()`
compares `$request->ip()` against a CIDR allowlist defaulting to `127.0.0.1/32`. If the proxy
forwards to loopback, `REMOTE_ADDR` is `127.0.0.1` for every internet request and the full
readiness detail is public.

`TRUSTED_PROXIES` is now read in `bootstrap/app.php`, empty by default so behaviour is unchanged,
and documented in `.env.example` with the loopback consequence spelled out.

### X-7 — nothing refuses `APP_DEBUG=true` in production (medium, fixed)

`config/app.php` defaults are safe, but `.env.example` ships `APP_DEBUG=true` and is copied
verbatim by `composer setup` and by every CI job. No probe checked the combination and no code
refused it, so an operator who sets `APP_ENV=production` and forgets the other line gets Ignition
stack traces, environment dumps, and SQL on every 500, with no signal from the readiness
endpoint. `EnvironmentProbe` now **fails** on it — for a product holding seal keys and signer
evidence this is not a preference — and `.env.example` says so beside the line.

### X-8 — inherited wildcard CORS (low, fixed)

There was no `config/cors.php`, so `HandleCors` fell back to the framework's packaged default:
`paths => ['api/*', 'sanctum/csrf-cookie']`, `allowed_origins => ['*']`. So
`Access-Control-Allow-Origin: *` was emitted for `/api/v1/*` and for the session-backed
`/api/auth/*` and `/api/passkeys/*` routes the auth package registers. `app/Http/Middleware/Cors.php`
existed, was a no-op pass-through, and was registered nowhere — dead code that read as though
CORS had been considered.

Impact was bounded: `supports_credentials` is false, so a browser withholds the session cookie,
and `/api/v1` needs an `Authorization` header an attacker's page does not have. But it was a
posture inherited rather than chosen, and the next person to enable `supports_credentials` would
have inherited `*` with it. `config/cors.php` is published and empty; the dead middleware is
deleted.

### X-9, X-10, X-11, X-14 — the small ones (fixed)

`routes/mail-webhooks.php`'s header block said **"NOT YET REGISTERED"** and explained how to turn
the routes on. `bootstrap/app.php` has registered them since it was written, and both endpoints
serve traffic. Neither is a vulnerability — both fail closed on an unset secret — but in a
repository where the route file is the stated authority on what protects a route, a header
asserting an endpoint does not exist is a review hazard. Corrected.

`shouldRenderJsonWhen` covered `api/*` and `functions/*` but not `webhooks/*`, which is outside
the `web` group and therefore has no session. A `POST /webhooks/mail/brevo` with a valid token
and a malformed body, sent without `Accept: application/json`, produced a `ValidationException`
that Laravel renders as `redirect()->back()->withInput()` — which touches the session store and
raises a 500 on a request that has none. Added.

`SigningUrlMinter`'s docblock says `MailContext` enforces three invariants: absolute, `https`
outside local development, and at most one query parameter. It enforced two.
`assertUsableActionUrl()` accepted `http` unconditionally. Now refused in production.

`withExceptions()` set no `dontFlash`, so the handler default covers only password fields. A
`code` longer than 16 characters fails validation and the submitted value is flashed as
plaintext into the `sessions` row — on a `database` session driver with `encrypt` off by default.
The OTP path deliberately re-renders rather than redirecting for exactly this reason; this covers
the shape refusal that happens before the controller runs. `code` added to `dontFlash`.

### X-13 — no dependency or static-analysis gate in CI (medium, open)

A grep across `.github/`, `composer.json`, and `package.json` for `composer audit`, `pnpm audit`,
`phpstan`, `larastan`, `psalm`, `trivy`, `snyk`, `codeql`, `gitleaks`, or `dependabot` returns
**nothing**. The `licenses` job checks license allowlisting and builds an SBOM, which is not a
vulnerability check. Static checking is `pint --test`, `tsc --noEmit`, and `eslint`.

For a product handling seal private keys, PAdES sealing, and evidence retention, `composer audit`
plus `pnpm audit` is the cheapest release gate available. Not added in this branch, because a
CI change that can start failing on a third-party advisory belongs in its own pull request where
the first failure is expected rather than surprising. (`composer update --lock` was run here and
reported no advisories against the current lock file.) Recorded in
[`release-gates.md`](release-gates.md).

### Checked and sound

Logging is the strongest part of this codebase. There is exactly **one** `Log::` call in the
whole of `app/`, and it records a credential prefix, a reason, an IP, a method, and
`$request->path()` — deliberately not `fullUrl()`, so a token in a query string cannot land in
it. `report()` appears once and only for an internal error. No `logger(`, no `Log::channel`, no
`dd`/`dump`/`error_log`/`print_r`, and no `fullUrl` anywhere. Token hygiene is structural rather
than conventional: SHA-256 verifiers, `SensitiveParameterValue` around the decrypted seal key,
`#[\SensitiveParameter]` on every token and OTP parameter, and an exception whose message quotes
a presented secret replaced with `previous` dropped. **There are zero CSRF exclusions** — the
routes that are not CSRF-protected are so because they are outside the `web` group, and each is
justified. The session cookie is pinned rather than derived from `APP_NAME`, host-only,
`HttpOnly`, `SameSite=Lax`, `Secure` by default in production, with `serialization => 'json'`
hardcoded. Health-probe failure messages were read one by one: none discloses a DSN, a host, a
path, a table name, a driver, an envelope title, a workspace name, or a storage key.
