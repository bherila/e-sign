# Stage 0 finding: PHP-only PDF import, geometry and anchors with tc-lib-pdf

Covers issues #4 (coordinate space), #5 (import fidelity) and #6 (positioned text
extraction for anchors). Read together with
[docs/preparation/coordinate-space.md](../preparation/coordinate-space.md) and
[ADR 0004](../adr/0004-pdf-engine-candidate.md).

**Recommendation: go, with three named gaps and one compensated engine defect.**
tc-lib-pdf can import, re-assemble and position content faithfully enough to build the
editor and the assembly pipeline on, and its parser is a sufficient basis for
deterministic anchor placement. Nothing found here needs a second engine. The gaps below
are real and none of them is silent.

## Method

The fixture matrix is generated by a committed script,
`tests/Fixtures/pdf/generate.php`, which writes 16 PDFs and a `manifest.json` describing
what each one contains. Regeneration is byte-reproducible except for
`encrypted-aes128.pdf`, whose AES crypt filter draws a fresh IV per string and stream;
its `/Encrypt` dictionary, the only part preflight reads, is stable.

The generator hand-rolls the PDF bytes rather than using tc-lib-pdf's writer, for two
reasons: several required
structures (cross-reference streams, object streams, encryption, signature dictionaries,
XFA, JavaScript, embedded files) cannot be emitted by the engine under test, and testing
an importer only against its own writer proves very little. Everything is synthetic,
including the embedded font: `tests/Fixtures/pdf/SyntheticTrueTypeFont.php` builds a tiny
TrueType program from scratch so no third-party font binary is committed.

Geometry is verified analytically, not visually. There is no container runtime and no
poppler on the development machine, and adding a rasteriser to CI just to compare pixels
would be a heavy way to answer a question that the file already answers exactly. Instead:

1. every source page carries a filled *probe* square burned into its content stream at a
   known native coordinate;
2. after import, `tests/Support/AssembledGeometryProbe.php` finds that square by
   composing the form XObject's `/Matrix` with the placement CTM and the output page's
   native transform — the same arithmetic a viewer performs;
3. a test *overlay* rectangle is drawn at a second known native coordinate and read back
   the same way;
4. positioned text runs are extracted before and after import and compared field by
   field.

If the probe, the overlay and every text run come back at the coordinates they went in
at, the page has not moved, been scaled, or been reflowed. A rasterised diff would be a
weaker statement, not a stronger one, because it would also fold in font rendering.

Reproduce with:

```bash
php tests/Fixtures/pdf/generate.php   # rebuild fixtures + manifest
php tests/Fixtures/pdf/measure.php    # the timing tables below
vendor/bin/phpunit tests/Unit/Preparation tests/Feature/Preparation
```

Everything scales linearly in page count: roughly **0.03 ms/page** preflight,
**0.27 ms/page** assemble, **0.93 ms/page** text extraction, and about **50 KB/page** of
peak memory on text-dense pages. A 200-page contract costs about a quarter of a second
of CPU and 10 MB. Image-heavy pages will be dominated by decoded image bytes instead,
which is why `PreflightLimits` caps the decoded stream size separately.

Suggested starting limits, to be revisited with real uploads: 32 MB upload, 500 pages,
100,000 indirect objects, 32 MB per decoded stream. These are the defaults in
`App\Domain\Preparation\Preflight\PreflightLimits`, and they are configuration rather
than an invariant.

## Findings

### 1. The importer ignores a nonzero page-box origin (defect, compensated)

`Com\Tecnick\Pdf\Import\Importer::importPage()` builds the form XObject `/Matrix` from
the selected box's **width and height only**. For a page whose CropBox is
`[36 48 576 744]` it emits `/BBox [36 48 576 744] /Matrix [1 0 0 1 0 0]`, so the imported
content keeps its source user-space coordinates while the destination page is sized to
540x696. The result is content displaced by the box origin and clipped at the page edge.
Measured on `cropbox-offset` page 1, a probe drawn at native (40, 40) lands at native
(76, -8) — 36 pt right, 48 pt up, with the top of the page cut off. The same error occurs
under rotation, where the matrix is built from the width alone.

The correct matrices, with `w = x1 - x0` and `h = y1 - y0`:

| `/Rotate` | correct | engine emits |
|---|---|---|
| 0 | `[ 1 0 0 1 -x0 -y0]` | `[ 1 0 0 1 0 0]` |
| 90 | `[ 0 -1 1 0 -y0 x1]` | `[ 0 -1 1 0 0 w]` |
| 180 | `[-1 0 0 -1 x1 y1]` | `[-1 0 0 -1 w h]` |
| 270 | `[ 0 1 -1 0 y1 -x0]` | `[ 0 1 -1 0 h 0]` |

They agree exactly when the origin is (0, 0), which is why the defect is invisible on
most documents.

`TcPdfAssembler::boxOriginCompensation()` applies the missing translation through the
placement matrix, which is a supported public API — the library is not modified or
vendored. The compensation is four lines, derived in a comment, and pinned by
`PdfImportFidelityTest::test_the_engine_still_ignores_a_nonzero_page_box_origin()`, which
asserts the *current, wrong* engine behaviour. If a future release fixes the matrix, that
test fails and the compensation must be removed. Preflight also emits a
`non_zero_crop_box_origin` warning so the condition is visible in the report.

This should be reported upstream.

### 2. `/UserUnit` is not carried into the output

The importer reads no `/UserUnit` at all — the string does not appear anywhere in the
tc-lib packages — and the writer emits none. A source page with `/UserUnit 2.0` produces
an output page with the same number of points and half the physical size.

This does not affect the coordinate space, because native units are default user-space
units by definition (see the coordinate-space document), and it does not affect field
placement. It does affect anyone who prints the assembled document. Preflight reports it
as a `user_unit_not_preserved` warning, and
`PdfImportFidelityTest::test_user_unit_is_not_carried_into_the_assembled_document()`
pins the behaviour. `/UserUnit` is rare enough (it only matters above the 200x200 inch
limit of default user space) that rejecting such uploads would cost more than it saves,
but the sender must be told.

### 3. Annotations and form fields are not carried into the output

Pages are imported as form XObjects, so widget, link and markup annotations are dropped;
only whatever they painted into the page content survives. `/AcroForm` does not appear in
the output at all. This is documented library behaviour, not a defect, and it is
survivable — our own signature fields are added by us, not inherited — but a source
document whose visible content lives in annotation appearance streams would lose it.

Preflight raises an `annotations_not_preserved` warning listing the count per page. A
future refinement could distinguish annotations that paint visible content from ones that
do not, and reject only the former.

### 4. Hazardous structures import silently

`already-signed`, `javascript-action`, `xfa-form` and `embedded-file` all import without
a single warning from the engine. `getWarnings()` returns nothing. Only encryption is
refused by the library itself. This is the strongest argument in this document for
running a real preflight parser before touching the engine: without it, a signed contract
would be imported, silently invalidated, and re-emitted as if nothing had happened.

`TcPdfPreflight` scans every parsed object, including objects inside object streams, for
`/Encrypt`, `/SigFlags`, `/Type /Sig`, `/ByteRange` + `/Contents`, `/FT /Sig` with a
value, `/XFA`, `/JS`, `/JavaScript`, `/S /JavaScript`, `/EmbeddedFiles`, `/EF` and
`/S /Launch`.

### 5. Encryption is refused, cleanly

`SourceDocument` throws `ImportUnsupportedFeatureException` on any trailer `/Encrypt`,
even for a document with an empty user password that every viewer opens without
prompting. Preflight rejects earlier and reports zero pages, so no geometry is ever
derived from a document that cannot be read.

### 6. Output is not byte-reproducible

Every assembled document carries a fresh `/CreationDate`, `/ModDate`, `/LastModified`,
document ID and XMP packet. The library documents pinning hooks (`setDocCreationDate`,
`setFileId`, `setDocumentId`), which will be needed for the sealing work, where the bytes
that get hashed must be stable. Not a Stage 0 blocker.

### 7. Content is preserved verbatim

On the positive side: the imported content stream is copied through unchanged. Text runs
extracted from the source and from the assembled output are identical in text, native
rectangle and direction on every accepted fixture, including rotated and offset-CropBox
pages. Fonts, including the embedded `/FontFile2` subset, and image XObjects come through
intact. Multi-page documents keep their per-page sizes. No reflow of any kind was
observed.

## Anchors (issue #6)

`TcPdfTextLocator` interprets page content streams directly: it runs the ISO 32000-1 9.4
text state machine over a real lexer, tracking the CTM, text matrix, text line matrix,
font, size, character and word spacing, horizontal scaling, leading and rise, and
computes each shown string's origin and advance from the font's own metrics. It recurses
into placed form XObjects, which is what makes it able to read an already-assembled
document. There is no regular expression over PDF bytes anywhere, compressed or not, and
no fuzzy or model-assisted matching.

Anchor semantics live in `AnchorResolver`, which is pure domain code with no library
dependency:

- **Match:** exact, case-sensitive substring of a decoded run. No whitespace
  normalisation.
- **Scope:** one page (1-based) or the whole document, declared.
- **Occurrence:** `sole()`, `index(n)` or `all()`. There is no "first match wins" default.
  `sole()` with more than one match raises `AmbiguousAnchorException`; `index(n)` beyond
  the match count raises `OccurrenceOutOfRangeException`; a required anchor with no match
  raises `AnchorNotFoundException`. An optional anchor with no match resolves to an empty
  result, which is the narrow, observable compatibility escape hatch the specification
  allows.
- **Offset:** in native units, from a declared corner of the matched text box
  (`AnchorOrigin`), never inferred from the sign of the offset.
- **Result:** a `ResolvedAnchor` carrying both the matched text rectangle and the placed
  rectangle, in native coordinates, to be stored on the review revision. Anchors are
  resolved once, before send; assembly uses the stored rectangle and never re-resolves.

Ordering is deterministic: by page, then top edge, then left edge, then character offset
within the run. `PdfAnchorResolutionTest` asserts that repeated extraction and resolution
produce identical output, and that anchors resolve to the same rectangles before and
after assembly.

Tested on eight fixtures, including a rotated page, a page with a nonzero CropBox origin,
a page with three occurrences, a page whose text comes from an embedded Identity-H font,
a scanned page, and documents using cross-reference and object streams.

**Rotated text is handled properly, not merely tolerated.** A run's direction is measured
in native space, *after* the display rotation, so horizontal text on a `/Rotate 90` page
is reported as `TextDirection::TopToBottom` and its per-character slicing runs down the
y axis. A run that is rotated off-axis is reported as `Other` and keeps its whole bounding
box rather than being sliced along an axis it does not follow.

### Limitations, stated honestly

- **Split runs.** One run per text-showing operator. A producer that emits a visible line
  as several `Tj` operators — very common with kerning, and normal for InDesign and
  LaTeX output — produces several runs, and an anchor string that straddles the seam will
  not match. Nothing here stitches runs together, because any stitching rule needs a gap
  threshold, and a threshold is a guess that would silently change which occurrence a
  signature binds to. A `TJ` array *is* treated as one run, since its numeric elements are
  kerning within one piece of text.
- **Ligatures.** A font that maps "ffi" to a single glyph yields whatever its
  `/ToUnicode` CMap says. A well-formed CMap decomposes the ligature and the anchor
  matches; a font with no `/ToUnicode` and a ligature in `/Differences` does not, and the
  run text will contain U+FFFD at that position rather than silently omitting a character.
- **Standard-14 fonts without `/Widths`.** Core font metrics are not bundled with
  `tc-lib-pdf-font` (no AFM files ship in the package), so a font dictionary with no
  `/Widths` array cannot be measured. The locator raises `TextExtractionException` rather
  than guessing a width, because a guessed advance silently moves the anchor box. Real
  producers almost always write `/Widths`, but this needs an AFM width table before
  general uploads are accepted. **Open gap.**
- **Encodings.** Simple fonts decode through `/ToUnicode` when present, otherwise a
  built-in WinAnsi table. `/Differences` is honoured only for `uniXXXX`-style glyph names;
  mapping arbitrary glyph names needs the Adobe Glyph List, which is not bundled.
  **Open gap**, and a smaller one than it looks, since producers that use `/Differences`
  normally also write `/ToUnicode`.
- **Composite fonts.** Only Identity-H and Identity-V CMaps. A predefined CJK CMap raises
  rather than mis-measuring. Type3 fonts raise for the same reason.
- **Scanned pages.** A raster page has no text layer and yields no runs. Anchors cannot be
  used on such documents at all, and no OCR is planned. The sender must place fields by
  coordinate. This is a product constraint, not a bug, and the editor has to say so.
- **Reading order.** Runs are ordered by geometry, not by any logical structure. A
  two-column layout will interleave columns in the occurrence ordering. Occurrence indexes
  are therefore stable for a given document but are not a reliable way to express "the
  second column's signature line"; page scoping plus a distinctive anchor string is.
- **Run boxes are typographic, not tight.** A run's rectangle is its advance width by the
  font's declared ascent and descent (0.8/0.2 em when there is no `/FontDescriptor`). It
  is what a person means when they point at a line of text, not a glyph bounding box.
  Within a run, a matched substring's rectangle is the run box divided evenly across its
  characters — exact for monospaced and Identity-H fixed-advance fonts, approximate for
  proportional ones. **Open gap**: per-glyph advance accumulation would make substring
  rectangles exact and is worth doing before anchors ship.

## Go / no-go

**Go.** No fixture failed in a way that blocks the pipeline. Specifically:

- geometry survives import exactly, for mixed page sizes, all four rotations, nonzero
  CropBox origins and combinations of the two;
- preview geometry and assembled geometry agree, because both are expressed in the same
  native space and the output page carries no residual rotation;
- visible content is not lost or reflowed on any accepted fixture;
- encrypted, already-signed, JavaScript, XFA and embedded-file inputs are all rejected
  with actionable messages — by our preflight, since the engine only refuses encryption;
- deterministic positioned text extraction is achievable in pure PHP at about 1 ms per
  text-dense page, and is good enough to build anchor placement on.

No alternative engine was evaluated, per ADR 0004, and none needs to be.

## Open gaps to carry forward

1. **Standard-14 font metrics.** Bundle an AFM width table (or reject at preflight) before
   accepting general uploads. Currently a `/Widths`-less core font makes text extraction
   fail for the whole document.
2. **Per-glyph substring rectangles.** Accumulate real advances inside a run so an anchor
   substring's rectangle is exact for proportional fonts.
3. **Adobe Glyph List.** Needed to decode `/Differences` glyph names when a font has no
   `/ToUnicode`.
4. **Upstream the page-box origin defect** and remove the compensation once it is fixed.
5. **Reproducible output.** Pin creation date, modification date, document ID and XMP
   before the bytes are hashed for sealing.
6. **Annotation triage.** Distinguish annotations that carry visible content from ones
   that do not, and reject only the former instead of warning about all of them.
7. **Real-world corpus.** Everything here is synthetic, as the repository requires. The
   limits table and the split-run limitation both need checking against a sanitised
   corpus of documents from real producers before general availability.
8. **Split-run policy.** Decide, with evidence, whether an explicit and observable
   same-line run-joining rule is worth the ambiguity it introduces, or whether anchors
   stay strictly per-run.
